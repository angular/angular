# A property binding bypasses an attribute resolver.

This diagnostic detects a property binding that writes an attribute which an attribute resolver on the same element resolves, such as `[title]` next to `(attr.title)`.

<!-- prettier-ignore -->
```angular-ts
import {Component} from '@angular/core';

@Component({
  template: `<button [title]="hint" (attr.title)="$event.resolve($event.resolver('Save'))"></button>`,
})
class MyComponent {
  hint = 'Save the draft';
}
```

## What's wrong with that?

An attribute resolver receives the attribute's sources: static attributes and `[attr.*]` bindings, plus `[class]` and `[class.x]` bindings for `class`, and `[style]` and `[style.x]` bindings for `style`.
A property binding such as `[title]`, an interpolation such as `title="{{hint}}"`, or an ARIA binding such as `[aria-label]` isn't a source, so the resolver doesn't receive its value.
The binding still writes the attribute, and its later writes can stay in the DOM while the resolved value doesn't change.

The diagnostic also checks properties that map to an attribute of another name, such as `[className]` for `class` and `[tabIndex]` for `tabindex`, translated interpolations such as `title="Hi {{name}}" i18n-title`, and the host bindings and host resolvers of the element's directives, including the ones that a directive inherits from its base classes.

## What should I do instead?

Bind the attribute instead, so that its value becomes a source of the resolver.
For `class` and `style`, a `[class]`, `[class.x]`, `[style]`, or `[style.x]` binding is also a source.

<!-- prettier-ignore -->
```angular-ts
import {Component} from '@angular/core';

@Component({
  template: `<button [attr.title]="hint" (attr.title)="$event.resolve($event.resolver('Save'))"></button>`,
})
class MyComponent {
  hint = 'Save the draft';
}
```

## Configuration requirements

[`strictTemplates`](tools/cli/template-typecheck#strict-mode) must be enabled for any extended diagnostic to emit.
To check the host bindings and host resolvers of directives, [`typeCheckHostBindings`](reference/configs/angular-compiler-options#typecheckhostbindings) must also be enabled, which is the default.

The diagnostic checks each template where a directive is used, and reports a directive's host binding on the element that the directive matches, once per template.
It doesn't check resolvers that automatic resolution adds, because the compiler can't see the resolvers that an application provides.
It doesn't check directives inside an `ngNonBindable` element, which Angular doesn't create, or the host bindings of directives and base classes from libraries.
It doesn't check a `@HostBinding` on a getter, because the compiler doesn't collect those host bindings for type checking.
It still reports a property that doesn't write its attribute, such as `[value]` on `<input>`, `[checked]`, `[selected]`, or `[muted]`, when the resolved attribute has the same lowercase name.

## What if I can't avoid this?

This diagnostic can be disabled by editing the project's `tsconfig.json` file:

```json
{
  "angularCompilerOptions": {
    "extendedDiagnostics": {
      "checks": {
        "propertyBindingBypassesResolver": "suppress"
      }
    }
  }
}
```

See [extended diagnostic configuration](extended-diagnostics#configuration) for more info.

For more information, see [Attribute resolvers](guide/components/attribute-resolvers).
